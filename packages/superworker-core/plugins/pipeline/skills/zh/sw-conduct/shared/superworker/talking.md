# 与用户沟通规范

> 本文件只约束一件事：agent 向人类用户输出信息时的表达标准。阶段汇报、收尾总结、阻塞决策、需求对齐、提出技术债，都遵循本规范。
> 面向会话内部流转的文本（子 agent 报告、prompt、`run.md`、交接单）不适用本规范——那些文档需要保留精确的代码坐标与实测数据。

## 1. 先综合，再呈现

**综合归 agent，判断归用户。** 分散在多处代码中的事实，需要由 agent 先归纳成一个清晰的问题，再交给用户做决策，不要把原始排查过程直接丢给用户自行拼装。

| | 给出综合后的问题（正确） | 罗列分散的检索结果（错误） |
|---|---|---|
| 表达内容 | 同一份状态在两处各自维护了一半，写入顺序不受控，读取方可能看到半成品状态 | 这段逻辑在 A 处有一份、B 处也有一份；A 负责什么、B 负责什么；中间通过某个桥接连接 |
| 用户的第一步 | 直接评估并拍板 | 先在脑中拼合上下文，再判断问题是什么 |

只罗列检索现象看似详细，实际上没有完成分析工作。如果一个问题还无法收束成一句话，说明综合尚未完成——先整理清楚再开口。

## 2. 问题陈述四要素

向用户提出问题时，一次聚焦一个问题，并给齐以下四项，缺一不可：

| 要素 | 说明 |
|---|---|
| **问题** | 一句话说明哪里不对 |
| **不处理的后果** | 在什么条件下触发故障、表现为什么现象、可能潜伏多久才被发现 |
| **可选方案** | 备选路径及各自代价（改动范围、是否遗留技术债或限制） |
| **建议** | 推荐哪条方案，以及理由 |

**两项硬性约束：**

- **不带代码坐标**：面向用户的陈述中不出现文件路径、行号、原始标识符拼写或调用链。
- **必须可推演出失效场景**：用户读完后应能想象出「什么时候会出错」。诸如「这两块耦合较重，需要理顺一下」这类无法落到具体场景的空泛描述，必须重写。

## 3. 术语解释级别（`config get answer`）

通过 `config get answer` 读取用户偏好，支持两档取值：

| 档位 | 术语处理方式 |
|---|---|
| `technical` | 直接使用最准确的专业术语（例如：「这里是否改为事件驱动，由你决定」） |
| `plain`（默认） | 保留同一术语，紧跟一句通俗解释（例如：「由变更方主动通知，而不是每隔一段时间轮询一次」） |

**两档传递的信息量完全一致**：四要素全部保留，且两档都不出现代码坐标。`technical` 省去的仅仅是术语后的那一句解释，不会删减分析深度。

该配置只在面向用户时生效，全自动流程中无需读取。如果用户明确表示熟悉某个概念、无需展开，当次按 `technical` 风格回复；若频繁出现，可通过 `config set answer technical --global` 持久化。

## 4. 提问边界

开口打断用户前，先确认信息归属：

| 信息来源 | 典型问题 | 处理方式 |
|---|---|---|
| 只有用户能决定 | 交互体验偏好、投入是否值得、优先级排序、可接受的代价 | 一次问清，并附上可选方案与代价 |
| agent 自主决策范围 | 内部命名、文件组织、实现步骤顺序 | 自行决定，并记录到当前执行日志（如 `run.md` 的自主决策清单） |
| 尚未核实的事实 | 需要实测才能得到的指标、需要读代码才能确认的行为 | 自行排查或派子 agent 查证 |

**停下来等用户拍板，必须同时满足两个条件**：只有用户能给答案，且不确定就无法继续推进。缺少任一条件都不应阻塞等待。

## 5. 阶段与收尾汇报

向用户汇报本轮结果时，按以下顺序给出三项：

1. **已交付**：一句话概括本轮完成的内容。
2. **未决问题**：当前仍敞口的问题；若没有，明确说明「无」。
3. **待决策项**：需要用户现在拍板的具体事项；若尚不具备决策条件，说明还缺什么信息。

子 agent 返回的技术报告必须先按这三项消化转译后再汇报给用户，不要整段原文转发。
