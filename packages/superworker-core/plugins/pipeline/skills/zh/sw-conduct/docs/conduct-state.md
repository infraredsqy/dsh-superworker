# conduct 状态与推进契约

> 本文件是 conduct 的**架构设计参考**：定义执行线模型、唯一状态写者以及各项关键设计取舍。
> 具体命令用法、字段名与输出格式不在此重复——以 `--help`、`plan --help` 与源码为准。
> 面向 conductor 的操作手册见 [`../SKILL.md`](../SKILL.md)；派发链见 [`conduct-dsh-dispatch.md`](conduct-dsh-dispatch.md)；节点 tag 与分流见 [`conduct-node-tags.md`](conduct-node-tags.md)。
>
> Agent 运行时不读取本文件——conductor 始终通过引擎命令层读写状态，绝不直接编辑 JSON。

## 0. 管线模型

一条 **cycle** 即一条执行线：它按序推进 DAG 节点（默认每次持有一个节点），选出节点交给独立会话执行，待会话回传结果后记账，再挑选下一个节点或停机。

```
cycle -> node -> （会话内部的准备 / 执行 / 复审 / 修复）-> 下一个节点 或 停机
```

节点内部如何分工由该会话自行管理，管线既不可见也不写入 `.superworker/`。管线记录仅维护三项信息：cycle 身份、当前持有的节点、已走过的执行路径。

管线自身只向 DAG 插入一种节点：由注册在**收尾（close）**时机的插件触发的维护节点。**插入动作只修改图**——建节点、连边、写 spec，不启动会话，也不改动 cycle 的当前持有关系。插入的节点挂在**本次收尾原本要开启的下一个节点之前**，因此随后的选点按常规排序会自动优先选中它，无需提前钉住。其余所有业务节点仍只由 `sw-route` 在用户确认后创建。

## 1. 三个角色

| 角色 | 承担方 | 职责边界 |
|---|---|---|
| 执行 | `sw-conduct` | 只干活、只交付事实。**支持独立运行**；内部自行编排 subagent |
| 记账与决策引擎 | 命令层（`packages/superworker-core/src/conductor.ts`） | **唯一允许写状态的一方**。所有可按规则计算的判断均在此完成 |
| 拍板 | 用户 | 仅处理规则无法算出的决策：确认自身需求、决定何时停机或放行 |

**凡能写成确定规则的判断，不应再消耗一次模型会话去重做。** 这条原则决定了整体分工：会话只交付它独有的产物（执行结论与现场测得的读数）；凡工具能算出的事项（挑哪个节点、插多少维护节点、是否触发维护、是否停机）一律不在会话内裁决。

## 2. 状态：一条 cycle 只有一份记录

cycle 的身份、当前持有节点与执行路径全部保存在同一条 cycle 记录上，不存在需要同步的第二份指针文件。所有状态变更必须经过命令层；手工修改会导致与工具视图分叉，连累后续 conductor。`.superworker/` 目录布局与版本库纳入规则，以 `init` 生成的 `.superworker/AGENTS.md` 及两份 git 配置文件为准。

关键设计约定：

- **认领记录在 `holding` 字段上**：同一节点同一时刻只能被一条 cycle 持有。正在执行不等于节点状态改变——图上节点仍保持 `todo`，归属关系是 cycle 的属性。两个事实分占两个字段，互不替代。
- **钉住即锁定归属**：归属在 `hold` 那一刻落盘，不等会话回报——因此执行中途改图不会把正在运行的这一步带偏。
- **路径全程追加保留**：同一节点重跑会产生两条步骤记录，判决逐条追加；读取方取最新一条，历史记录用于解释执行轨迹。
- **判决与节点状态分属两套词表**：会话在交接票（ticket）上写入的是判决（是否交付）；图上节点只有「在局中 / 出局等人 / 已完成」三态。交接票落盘意味着该节点只剩收尾；重试留下的标记**恒视为红灯**——未清理前，后续读取方会一直等待。
- **仅有一类数值需要会话上报**：交接票上的其余键原样落盘、工具不校验；唯一例外是插件声明为度量的读数——且仅当该度量绑定了某个配置旋钮、且该旋钮在解析链上存在有效值（由某层显式配置或声明带默认值，见第 9 节）时才会向会话索取。由插件工具自行计算的指标不经交接票，也不会询问会话。**报数方不拍板，拍板方不采数。**
- **派生状态不落盘**：「就绪」「运行中」均为读取时实时计算的派生标签。

## 3. 会话唤醒、上下文注入与收尾顺序

**prompt 仅包含单行调用命令**，不含冗余上下文：节点标题、spec 路径与收尾命令由会话自行读取；用户指令不拼入 prompt，而由宿主随每轮上下文动态注入（无可见指令或关闭 `injectInstructions` 时注入零字节）。把动态信息拼进静态 prompt 只会留下过期副本。

**指令约束由宿主按位置动态注入**：每个会话（包括 conductor 及其派发的 subagent）每轮都会收到与当前位置执行 `instruction list` 完全一致的约束清单。无可见条目时，命令输出「无指令」提示，而宿主注入零字节；关闭 `injectInstructions`（默认开启）时同样注入零字节。
- **位置判定**：指令仅分 `global` 与 `cycle` 两级。宿主依据当前会话处理的节点锁定其所属 cycle，绑定到其他 cycle 的指令既不会注入当前会话，也不会在当前 cycle 收尾时触发拦截。
- **歧义保守策略**：当多条 cycle 并行且无法确定当前节点归属时，**宁多勿漏**——漏拦一条真实约束的代价远高于多读一条无关提示。可见性完全动态推导、不落盘，因此不存在范围结束时的清理负担。

**指令清单的增删归档仅归用户**：归档会保留条目但停止注入；删除会移除正文，仅保留 `id` 与时间戳墓碑用于跨机合并——防止另一台机器 pull 时把已删条目重新带回，也避免编号复用。墓碑不出现在人类视图中，删除也不是第三种状态。恢复归档同样只能由用户操作，会话无权增删改。

**收尾顺序严格固定**：执行 `handoff`（写交接票）与 `settle`（关节点）之后，顺序锁定为 **`git commit` → `git push` → `advance`**。下一会话会在同一工作树启动并率先 `pull`；若工作树未提交干净，下一会话会拉取失败或读到半截状态。因此**推进管线永远是最后一步**。`settle` 本身不钉节点、不开会话，仅在阈值越界时向图插入维护节点；钉住与派发由独立的 `advance` 命令完成。将写票与收尾拆成两步，也是为了让「票已落盘、节点未收尾」的中间态稳定可观测，便于中断恢复。

**交接票本身不驱动管线**：写入交接票后，会话仅读取下一步提示（即「等待收尾」与 `settle <node>`）便交回；关闭节点由 `settle` 完成，钉住节点、生成 prompt 与拉起会话均由 `advance` 链路完成。写交接票的动作绝不写 prompt。

**不复活旧会话**：每次执行均开启新会话，避免上一节点的对话上下文污染下一节点。

**命令由工具执行，会话只读 `action`**：工具返回的动作不携带待执行的 shell 命令字符串；所有写入口仅在真正变更指针、交接票、路径或 cycle 状态时才返回成功，否则直接抛错。所有外部探查均带超时上限：例如 `doctor` 调用 git 超时会直接标红并报告等待时长，不会无限挂起。

## 4. 收尾入口与推进入口

`settle <node>` 用于收尾单个节点；`plan` 用于查看下一步；`advance` 是组合命令，按序一次完成钉住（`hold`）、落盘派发材料与启动会话（`dispatch`）。标准流程也可分步执行 `plan` → `hold <node> --cycle <id>` → `dispatch <id>`，中间可随时停下检视。

两个入口对「cycle 是否处于服务中（`active`）」的处理不同：

- **`settle` 不受 cycle 状态限制**：节点自身已标明归属；若已停机的 cycle 连正在持有的节点都无法收尾，该节点会永久卡死。当 cycle 非 `active` 时，`settle` **只做记账**：记录步骤、更新节点状态、执行收尾插件接缝，但不钉住下一节点、不开会话，也不改动 cycle 状态——是否重新启用完全由用户决定。
- **`worktree_mode` 不改变收尾的读盘逻辑**：`worktree_mode` 仅支持 `off` / `fork`（git 项目默认 `fork`，非 git 项目默认 `off`，可在项目层或全局层覆盖，见第 8 节）。读到 `reuse` 会直接拒绝（`worktree_mode_unsupported`）。创建、合并与清理 worktree 均由会话执行 git 命令完成，工具只管记录与命名，收尾不检查工作树状态。
- **`advance` 绝不驱动非 `active` 的 cycle**：遇到停机状态会返回 `ask_user`，并附上重新启用的命令。

**工具绝不擅自将 cycle 置为 `active`**：cycle 创建时即处于 `active`，一旦停机只能由人重新启用。停机原因不存入状态字段，而体现在停机时的提示信息中。图上暂时无就绪任务不代表 cycle 已死亡——图会继续生长，是否续跑由人拍板。

`sw-route` 替用户执行启用命令同样遵守此原则：决定来自用户，`sw-route` 只是代为落盘。规划节点时即同步敲定所属 cycle，使后续 `/sw-conduct` 启动时面对的是明确状态，无需猜测。

## 5. 结论判定与停机规则

- **交付结论以盘上交接票为准**：工具直接依据交接票更新节点状态，不二次追问其他会话。交接票记录粗粒度结论，细粒度依据保留在会话报告中。
- **未交付时的续跑策略归 cycle 所有**：由 cycle 的 `when_shelved` 决定是停机等人，还是照常推进下一节点。无论取何值，未交付节点本身都会出局等人。
- **停机点先看节点自身的 `mode`**：`auto` 无人工停点；`manual` 的确认点在会话对话内；`checkpoint` 的确认点在收尾之后——跑完本节点即停机，等待用户说「继续」。cycle 的 `stop_after_nodes` 只能在 `mode` 之上叠加额外停点，不能放宽。手动停机使用 `cycle status <cycle> inactive`。
- **用户放行会被持久化记录**：`checkpoint` 闸门落在 cycle 状态上，当用户重新启用该 cycle 时，工具同时将该节点的**本次交付**标记为「已获人工批准」（判据为批准时间不早于本次交付时间，两者均记录在节点自身）。批准**按交付计、不按节点计**：若同一节点重新交付，交付时间会晚于旧批准，旧批准自动失效，无需手工撤销或维护第二份记录。由此可明确区分「人已放行但图暂时无活」与「管线等待人工放行」。不经 cycle 单独审批某节点可使用 `dag approve`。
- **停机只有一种状态**：计划决定停机时将 cycle 设为 `inactive`。不区分 `paused` 与 `completed`——因为 DAG 会不断新增节点，所谓「已完成」随时可能变化。
- **选点排序全局唯一**：工具直接复用 DAG 侧的全量排序，仅按就绪状态与本 cycle 过滤集筛除行，绝不重写打分逻辑，避免两套排序各自漂移。

## 6. 核心不变量

以下不变量均源于真实线上缺陷，必须严格遵守：

1. 终态交接票是「节点已完成」的唯一凭证；重试标记恒视为红灯，替换前必须先回卷交接票。
2. 「已交票但未收尾」是一个**稳定状态**：重复查询始终返回相同的等待提示与 `settle` 命令，不写任何字节。
3. 收尾单个节点 ≠ 结束整条 cycle：同线其他节点不受影响，各自按独立收尾节奏接力。
4. `stop_after_nodes` 只能在节点 `mode` 基础上收紧停点，不能放宽。
5. 各工具只读各自账本（DAG 侧不读 cycle 记录）：只有同时读取两份账本的读者才能拼出「当前谁在执行哪枚节点」。

## 7. 故障恢复

**重跑节点的统一路径**：先执行 `cycle retry <cycle> <node>` 回卷交接票（若会话已死且 `started` 仍在盘上，加 `--drop` 一并清除认领），将节点放回就绪队列，再重新 `hold` 并 `advance`。历史判决逐条追加，工具只看当前持有关系。

**链条断裂时的明确拒绝**：会话未写交接票即调 `settle` 会当场报 `nothing_to_settle`；派发失败则原样透传错误理由（面板展示给用户，自动接力仅记日志）。`started` 是唯一的「已启动」证据：未落盘时 `plan` 仍视为待派发；已落盘但会话确已死亡时，必须先用 `cycle retry <cycle> <node> --drop` 撤销认领，再按正常流程重钉与推进，严禁强行重复派发。

**刻意不设常驻 watchdog**：常驻监控需要额外维护后台守护进程。因此若某会话中途卡死且未写交接票，管线不会自动检测，只会静默停在该节点等待人工介入，手动运行 `/sw-conduct` 即可接手恢复。

## 8. 配置系统：五层解析链

**每项配置即一个旋钮（knob）**，类型仅限四种：数值（number）、整数（integer）、枚举词（word）、开关（switch）。旋钮有两个来源——核心内置配置与已安装插件在声明中注册的配置——合并为同一张全局表，每个名称仅有唯一所有者。**核心配置与插件配置走解析链，而 cycle 自身的四项策略不走解析链**（见本节末条）。

- **五层优先级（窄覆盖宽）**：单节点 → 当前 cycle → 当前项目 → 本机全局 → 出厂默认。同一旋钮可在多层同时配置，生效层级完全确定。
- **层级约束（`layers`）**：并非所有旋钮都允许落在全部层级。核心内置旋钮（`max_agents`、`test_tier`、`worktree_mode`）仅允许项目层与全局层；插件旋钮默认支持全部四层可写层级，但插件声明可通过 `layers` 收窄。若有人手工把旋钮写入不被允许的配置文件，读取时会当场报出旋钮名并跳过，绝不静默忽略。
- **读取必给来源**：每次读取返回「生效值 + 来源层级」，直接回答「为什么我的配置没生效」。`config list` 输出键值对与来源，`config get` 仅输出值供技能解析。
- **写入仅两条命令**：`config set` 仅写入单个层级，`config unset` 移除该层配置使更宽层级重新生效。写入不允许的层级会被拒绝并提示合法层级。开关的 `off` 是显式值（表示关闭），移除配置才用 `unset`。未指定层级旗标时默认写入项目层；cycle 层配置存储在 cycle 记录上，由唯一写者写入。
- **严格报错**：文件层出现无法解析的值时立即报错退出，绝不静默回退到出厂默认（否则会误导用户以为从未配置）。唯一例外是 cycle 层：作为状态记录采用宽容读取，无法解析的值视作未配置。
- **默认值可选**：插件阈值既可不设 `default`（未配置时显示为横线 `-`，不触发判定），也可设 `default`（安装即生效，交接票表单随之索取对应读数）。判定逻辑与表单索取读取同一数据源。
- **cycle 的四项独立策略不入解析链**：`parallel`（最大并发持有数）、`when_shelved`（节点未交付时停机或续跑）、`stop_after_nodes`（跑满指定节点数后停机）与 `model`（会话使用的 `provider/model` 路由）直接存在 cycle 记录中，仅通过 `cycle policy` 读写。`config` 不识别这四个名字，写在项目层或全局层不会生效。

## 9. 插件（Plugin）与维护通道

**一个插件即一个目录**：`plugins/<name>/` 包含三类内容：
1. **声明（`plugin.json`）**：纯数据，声明介入时机、注册的旋钮与读数名、产出的动作、去重标签以及度量对应的技能方法名。
2. **实现（`impl.mjs`）**：代码逻辑，在声明的时机被宿主调用；附带工具文件通过 `files` 字段声明。
3. **随附技能（`skills/<lang>/<method>/`）**：由宿主 `src/host/skills.ts` 中的 `installPluginSkills` 按当前语言整目录拷贝至 `<dshHome>/skills/<method>/`，并在 `<dshHome>/superworker/skills.json` 记录清单，随插件同步安装与卸载。

目录名即插件唯一身份：删除目录即彻底卸载，放回即恢复，无需修改任何核心代码。

**核心只认类型闭集，不硬编码插件名**：闭集包含四类旋钮、两个时机（收尾 `close` / 派发 `dispatch`）与两个动作（插入 `insert` / 拦截 `block`）。合法组合仅有两种：**收尾时插入、派发时拦截**；声明越界时运行时跳过，体检（`doctor`）点名报错。旋钮名、读数名、读数来源、去重标签、方法名及技能名均由注册表（`packages/superworker-core/src/plugins/registry.ts`）校验唯一性，严禁跨插件重名或借用。声明是静态数据，列出插件或打印帮助时绝不执行实现代码，单个损坏插件不得拖垮帮助与体检。

**读数来源归属明确**：读数要么由执行会话上报，要么由工具计算。核心仅内置一种默认来源；插件如需自定义指标，须在声明中认领专属来源名并指向 `impl.mjs` 中的计算函数。核心不解释返回值，仅透传结果，类型异常时按「本次未知」处理。来源名由认领插件独占，不得借用其他插件的来源名——越界引用在体检中报错，运行时跳过该插件而不阻断管线。

**插件可注册自定义命令词**：声明可绑定命令词（`<word> ...`），触发时将命令行交由 `impl.mjs` 的 `main` 执行。仅提供命令词的插件无需声明管线时机与动作；未注册命令词的插件则必须完整声明时机与动作。命令归属、帮助文案与冲突裁定均可在 `doctor` 输出中查看。

**收尾插入机制**：`settle` 直接调用所有收尾时机插件，单次收尾中每个触发的插件最多贡献一个节点（多条指标同时越界则同时插入多个兄弟节点）。插入的节点挂在原本下一个节点之前，自动在下次选点排第一。**若插件希望管线继续推进，必须在已有未完成维护节点时停止重复触发**（通常借助去重标签判断），核心不会替插件猜测。

**运行时宽容，体检严格**：
- **运行时**：声明损坏直接跳过；实现加载失败、抛错或调用 `process.exit` 时，在收尾/派发返回值中附带 `WARNING:` 数据供调用方展示，不影响其他插件与主流程——正在运行的项目绝不能被单个坏插件卡死。
- **体检（`doctor` 与测试共用同一验证器）**：严格校验闭集合法性、跨插件命名冲突（含读数来源与技能名）、实现文件可加载性、声明的来源函数存在性（只检存在不实调）、方法对应技能是否位于本插件目录内（未被方法引用的独立用户技能合法），并用虚拟项目实调一次实现确认其不抛错且不私自改图。校验绝不在管线运行路径上触发。

**开关即 `switch` 旋钮**：沿第 8 节五层解析链生效；未声明开关的插件默认常开。宿主 `enabled()` 在调用插件前统一判定，开关关闭或不可读（视为 `off`）时整轮跳过，插件实现无需自行感知开关状态。

**派发拦截闸门**：派发时机插件可返回拒绝并附理由（写入 `dispatch_blocked`），同时保持 cycle 为 `active`（适用于时间窗限流等「稍后再试」场景）。闸门必须是**轻量、幂等、只读**的检查，由 `conductor.dispatch` 在读取认领之后、落盘材料与启动会话之前调用——被拦截时不写 prompt、不开会话，已钉住的节点保持不动，待下次派发再查。禁止在闸门内计数、写盘或因重复查询改变结论。

### 维护通道

**维护通道上的每笔技术债，对应插件声明中的一条度量指标**。收尾时机插件在节点收尾时检查当前读数是否触及或超过阈值（阈值定义为「仍可接受的上限」，读数 ≥ 阈值即越界）；越界则请求插入一个维护节点。**每笔债自量自判**：数据来源、判定规则、文案模板与还清标准均归对应插件所有，彼此独立。

- **项目级债务入口**：维护任务本身无业务依赖边，常规排序总是垫底。维护通道在收尾阶段按当前 cycle 配置的阈值将其动态插入队列。
- **各自独立判定**：开关、阈值、去重标签与方法名均归各插件私有（`doctor` 可列出全貌）。单次收尾中多条指标同时越界会同时插入对应数量的节点。
- **在可计算处决策**：收尾阶段结合交接票与图快照完成判定，会话只负责上报可测读数，不决定是否触发维护。
- **零配置回归底线**：未配置阈值的指标不生效，收尾返回值与无该插件时逐字节一致；开关为 `off` 时同样不触发、不采数。
- **精准插队不改排序**：插入的新节点仅增加一条边（`维护节点 → 原本的下一节点`），图评分算法自动将其推至队首，无需修改任何排序代码。
- **同批插入互为兄弟**：同一次收尾插入的多个维护节点均指向同一个后继节点，彼此无先后依赖。
- **继承当前 cycle 的 tag**：新节点自动携带当前 cycle 的 tag，确保其落在本 cycle 的选材范围内而非被过滤隐藏。
- **去重防泛滥**：借助去重标签，同一指标在图上同时最多只存在一个未完成的维护节点；已有节点未清完时，再次越界暂不重复插入。
- **标准化的生成 spec**：生成的 spec 遵循普通节点规范——单句范围说明（仅将该指标拉回阈值内）、可执行的完成判定、触发原因（指标名、当前读数与阈值）以及指向方法技能的声明行。模板绝不猜测实现细节（不写函数名、文件路径或行号）；无法写成明确判据的工作不进入维护通道。
