# sw-conduct 常见反模式

开工前对照检查。本文件仅收录**工具不会当场拦截、但执行过程中容易无意识触发**的问题；完整判据见 [`./SKILL.md`](./SKILL.md)。

## `conduct-treats-critical-as-false-positive` · 指挥者自行裁定复审结论为误报

**症状**：不认同复审指出的问题，自行判定为「误报」并直接放行。

**纠正信号**：报告中声称「该项为误报」，但从未重新发起复审以证实。

## `conduct-polls-for-subagent-completion` · 通过轮询等待 subagent 完成

**症状**：派发 subagent 后，反复用 `Start-Sleep` 配合 `Test-Path` 检查产物，或循环调用 `list_agents`。等待时长全凭估算（如 90 秒、240 秒），白白消耗实测耗时，还把轮询日志当成「进度」。

**示例**：某节点会话中累计了 22 段同类等待，每段都标注 `# wait-guard: 必要等待 - 等某 subagent 写出 report.md`。

**纠正信号**：日志中成对出现 `Start-Sleep` 与 `Test-Path`。`# wait-guard:` 仅用于退避重试、限流窗口等确实需要等待时间的场景。

## `conduct-flat-count-read-as-convergence` · 将复审计数持平误判为收敛

**症状**：复审连续多轮报 `critical=0, minor=10`，指挥者见数量未上升便继续派发下一轮；或同一处反复修改三四次、每轮在其他位置冒出新 critical，仍机械照单修改。

**纠正信号**：复审首行的定位标记连续两轮落在同一批位置上。

## `conduct-constraints-without-provenance` · 未标注约束出处，将自推约束当成硬约束

**症状**：某个节点的会话自行推算出一项预算或上限，写入文档时采用了与用户需求相同的强制措辞；后续节点逐层引用，最终演变成谁都不敢触碰的硬约束。

**示例**：某项目的目标文档（`goals.md`）从未提及「章／段／位子」，全部约束都停留在体验层；「一章最多三段」是 `layout-budget.md` 节点自行推算的数字，随后被 `section-spec`、`render`、`diff-check`、`outline` 逐层引用，最终与另一条自定规则「指定图占满开篇章」冲突，跨两个节点空转了五轮。

**纠正信号**：文档中出现「必须／不许／一律／上限为」等硬性表述，但翻遍用户原话与目标文档都找不到出处。

## `conduct-freezes-criteria-with-findings` · 将判尺与上一轮的边界一起冻结

**症状**：把「逐字一致」误解为「补充约束永远不变」——明明边界已经调整（如解冻某一行、收缩范围或引入了新的用户判据），下一轮复审 prompt 里的判尺却一字未改。复审依据过期标准报出问题，指挥者又将其当作交付缺陷派发修复。

**示例**：某节点第二轮裁定「清除该目录下那行旧名注释，其余保持冻结」并交由 fix 执行；第三轮复审的补充判据仍写着「该目录下任何改动均为 critical」，导致复审报出一条 1 行增删、零运行时影响的 critical，最终被用户驳回。

**纠正信号**：本轮复审判尺中的某条规则，与上一轮下达给 fix 的裁定相互矛盾。

## `conduct-hand-edits-ledger-or-resolves-conflicts` · 手工编辑 `.superworker/` 记录或自行拼接合并冲突

**症状**：为了让两侧图状态对齐，直接读写 `.superworker/` 下的记录文件；或 pull 遇到冲突时，按行手工拼接两份 JSON。

**纠正信号**：工作区出现手工改动过的 `.superworker/` 记录文件，或被按行拼接的 JSON。
