# 超级工坊设计哲学

> 本文件描述超级工坊的设计主旨与底层原则，供 `sw-route` 引用，不重复操作细则。

## 核心问题

真实工程很少能在单轮或单个会话内一次完成。一旦工作拉长到包含依赖关系的多步链条（4 步、8 步、10 步乃至更长），常规使用方式会落入两难：

- **人工分会话推进**：每完成一步都需要人回到对话里验收结果并下达下一步指令，人被迫充当全天候监工。
- **单会话硬扛全流程**：即便引入 subagent，链路拉长后主上下文仍会逐渐漂移、累积冗余信息，最终失去对全局的把握；执行途中发现的库内既有问题也无处安放，只能被忽略或打断主线。

## 核心设计：常驻的共享编排面

超级工坊的核心只有一件事：把原本需要临时编写脚本（如一次性 workflow）或留在聊天记录里的编排逻辑，沉淀为一套**常驻在项目内、agent 顺手可调的接口，并辅以面向用户的可视化面板**。

人与 agent 共享同一份持久化的结构化状态（`.superworker/`）：

- **规划与执行分离**：先把目标、边界与验收口径谈清楚并落成节点，再交给执行管线推进；人的精力集中在前期方案对齐、显式停点决策与最终验收。
- **跨会话持续推进**：每个节点在独立的新会话中运行，互不拖累上下文，状态全程落盘、可观测、可随时中断或从任意节点续传。

## 为什么底盘是 DAG

任务之间存在天然的先后依赖（B 依赖 A，或并行分支在 C 处汇合）。线性列表会丢失这种结构，手工维护的优先级也会迅速过时。

图的拓扑结构自动为**未完成**节点推导两个核心指标，并在上游完成后动态更新，无需人工调整：

| 指标 | 含义 | 图算法 |
|------|------|--------|
| **urgency**（紧急性） | 现在能不能开始做 | 拓扑位置靠前 = 前置依赖已满足 = 越 urgent |
| **importance**（重要性） | 有多少工作依赖它 | 反向可达集越大 = 被越多节点依赖 = 越 important |

两者共同决定默认排序（`urgency × importance`）：前置已清且影响面广的基石节点优先推进，前置未清的高影响节点则先解其上游。同时，依赖边也明确标出了节点间的先后边界，使互不依赖的节点具备并行推进的条件。

在记录策略上：

- **节点状态留痕而非删除**：已完成（`completed`）或搁置（`shelved`）的节点保留在原位以维系历史与依赖引用；只有想法本身作废、确认移出计划时才真正删除。
- **计划与现状隔离**：未来计划与执行过程全部收口在 `.superworker/`，项目文档（`docs/`）只保留已实现的现状，避免 agent 混淆“计划”与“事实”。

## 两个关键延伸机制

### 独立复审：长链条上的 fail-safe

在复杂工程的多步执行中，执行者难免产生局部疏漏。如果缺少独立校验，单步的细微偏差会沿着依赖链向下游持续放大。

因此管线在节点收口处引入独立的复审与修复闭环，作为长链无人值守运行时的**容错机制（fail-safe）**。它服务于长程稳定性，而非系统运转的硬性前提——在需要快节奏试错的场景下可以放轻或跳过复审，但相应的稳定性保障也会随之收窄。

### 外置大脑：持久化图的自然收益

当计划与问题都有了常驻的结构化落点，系统自然具备了“外置大脑”的能力：推进任务 A 时冒出的 B / C / D 想法，或执行途中撞见的存量隐患，都可以直接落成节点挂上依赖或记入问题池，既不打断当前工作节奏，也不会在会话切换后遗失。对需要多线程推进复杂项目的工程师，这一层收益尤为明显。
