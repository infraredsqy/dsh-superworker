# 落线、校验与起跑

> 何时读本文件：第五步收尾时，用户要求**立刻起跑**（未说「先别跑」）。若只建图/改图不起跑，跳过本文件。

落线与起跑分两步：**落线只写记录、不开会话；起跑才开出 `/sw-conduct` 会话**。所有涉及恢复旧线或开新线的决策，必须在第三步经用户确认，这里只负责执行。

## 1. 落线

- **恢复已有非活跃线**：
  ```pwsh
  cycle status <line> active
  ```
- **开新线（常规，按排名自动挑选节点）**：
  ```pwsh
  cycle start <slug> --title "<用户原话>" --tags <tags>
  ```
  建线并按排名钉住头几个节点（`--parallel` 默认 1）。
- **开新线（用户明确点名只跑某一个节点）**：
  ```pwsh
  cycle create <slug> --title "<用户原话>" --tags <tags>
  ```
  只建线，不预先钉节点，留给第 4 步 `hold` 指定节点。

`--tags` 必填，必须与这批节点的 tag 匹配。`cycle current` 的 `Node:` 行与 `cycle start` 输出的 `STARTED:` 仅表示线已握住的节点，会话要到第 4 步才会真正打开。

## 2. 提交记录

按主文件第五步完成两笔提交（图/spec/cycle 记录一次，以及「现在就做」的产出一次）。确保记录已落库后再起跑。

## 3. 校验就绪状态

运行：
```pwsh
plan --cycle <line> --json
```
（只有一条活跃线时可省略 `--cycle`。）

- 输出必须指向一个可派发的节点。
- 若图里没有就绪节点，先回去补图；若被 tag 或闸门拦下，照实向用户说明 `reason`——**绝不递出一条跑不动的指令**。
- 若用户点名了具体节点，额外用 `dag info <node_id>` 核对：必须为 `todo` 且所有依赖均为 `completed` 才能起跑；否则向用户说明当前阻塞状态，等就绪后再跑。

## 4. 起跑

- **未点名具体节点（默认）**：
  ```pwsh
  advance --json
  ```
  钉住当前线的可用槽位、落地各自 prompt（`/sw-conduct <node_id> [pipeline]`）并交给执行器开出会话。
- **用户点名了某一节点**（「开启这个节点」「直接开它」）：
  ```pwsh
  hold <node_id> --cycle <line>
  dispatch <line>
  ```
  跳过排名直接钉住并派发该节点。
- **线手里已握着其他节点**（`cycle current` 的 `Node:` 已有节点）：**不要再 `hold` 第二个**（`dispatch` 会把手里所有节点一起派出去）。先把现状摆给用户，由用户决定先跑哪一个。
- **遇到 `spawn_error`**：说明当前进程没有原生 opener，会话未打开、节点仍处于待跑状态。转第 5 步交钥匙，并在报告中如实说明。

## 5. 交钥匙（仅当第 4 步未能开出会话时使用）

在报告末尾给出一条可直接回车运行的指令：
- 指向具体节点：`/sw-conduct <node_id> [pipeline]`
- 由活跃线自动按序挑选：`/sw-conduct`

**`[pipeline]` 不可省略**——省略后该会话只跑完当前单个节点即停，不会接续收尾、提交推送与下一节点。若线仍处于非活跃状态，不要给运行指令，直接向用户说明当前状态。
