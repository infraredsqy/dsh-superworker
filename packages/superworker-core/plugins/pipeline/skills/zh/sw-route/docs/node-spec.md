# 节点规格编写指南（`intention.md` / `spec.md` / `method:`）

> 何时读本文件：准备落笔创建节点的 `intention.md` 与 `spec.md`，或需要创建 `method:` 清债节点时。

## `intention.md` 与 `spec.md` 的分工

把「目标/原则」和「当下现状的展开」拆成两份文件，避免 agent 把两层混读成同一层，导致判据过期却无人察觉。

| 维度 | `intention.md` | `spec.md` |
|---|---|---|
| 回答什么 | 要什么、不要什么、**为什么** | 改哪一块、边界在哪、怎么算完成 |
| 谁能改 | **仅用户** | 执行侧仅在现状变化导致快照过期时刷新 |
| 代码库演进后 | **不变** | 其中的数字/清单会过期，需同步更新 |
| 判断标准 | 新增模块、页面或数据文件后是否依然成立 | 依赖的是写这份文档那一刻的现状 |

### `intention.md` 怎么写

- 写清这个节点要维护的目标与原则（例如「状态变更只走事件驱动」「该功能仅作用于真实编辑页，模拟页作为对照组保持不动」）。
- 描述「我们想要的世界」，不描述「当前代码长什么样」。
- 格式不限（散文或条目均可），唯一硬要求：**读者能回答「为什么」，而不只是「做什么」**。
- 自查：如果某句话是在描述当前现状，把它挪到 `spec.md`。
- **为什么 agent 严禁修改 `intention.md`**：它是用户拍板的基准。agent 改了它，就等于悄悄替换了用户需求，后续所有复审和验收都会建立在被篡改的基准上。若发现世界已变、判据覆盖不到或意图本身有矛盾，必须停下来把新现状与 `intention.md` 一并摆给用户裁定。

### `spec.md` 怎么写

- 写清改动落点（用项目术语，**可写文件夹与文件名，严禁写函数名、调用顺序与实现步骤**）、只读参照基准、范围边界，以及匹配真实判断方式的完成判定。
- **只读参照优于文字转写**：仓库内存在现成参照物（原型页、设计稿、样本、外部规范）时，直接给出路径并说明哪些不搬（如假数据、演示代码），**不要把参照物压缩成几行抽象摘要**。项目若规定「工程代码不得引用某目录」，约束的是运行时代码，不禁止 `spec.md` 指向它作只读参照。
- **写清换新还是沿用**：如果旧骨架、旧样式或旧结构需要整体替换，明写替换要求，不用含糊的「照旧」把新任务锁死在旧壳里；上游立了共用契约（如共享视觉变量、统一协议）时，下游显式声明消费它并清理旧私有定义。
- `spec.md` 不可避免会带有写作当下的快照信息（模块数、文件清单、当前读数）。凡是写到数字、名单、枚举的地方，写得让执行侧能一眼判断「这个数有没有过期」。
- **刷新而不膨胀**：执行侧若发现现状已变导致快照过期，只更新现值（改动随节点提交进入 `git diff`），**不写历史流水账**（不要写「原来是 A，现在改成 B，因为……」）。
- **spec 全绿不等于 intention 达成**：若判据已覆盖不到 `intention.md` 的原则，仍算交付缺陷。
- **老节点兼容**：没有 `intention.md` 的历史节点，将整份 `spec.md` 视同 `intention.md`（严格只读）。

## 可选节：「不做的事」

仅在讨论中**确实否决过具体方案**时才写这一节：一行一条，写清「被否决的做法 + 一句理由 + 出处（用户拍板 / 现有代码 / 硬边界）」。

- 没有被否决过的方案就不写，不要凑数，也不要把后续节点的内容填进来。
- 拍板往往伴随排除，排除项最容易在跨会话时遗失；只要讨论里真排除过，就记下来。

## 清债节点（`method:`）

当节点用于清理某类记录中的一批债时，**不要自己手写清债步骤**：

1. 先运行一次 `doctor`，查看已安装的插件、每个插件声明的**去重标签**和**方法名**。
2. 在 `spec.md` 中写入一行 `method: <方法名>`（原样照抄 `doctor` 输出的方法名）。这行指令表示「由指挥者按该技能直接执行」，优先级高于 `weight`（见 [`../../sw-conduct/SKILL.md`](../../sw-conduct/SKILL.md) 的「方法」）。
3. 节点标签必须同时包含**该度量的去重标签**和**所属 cycle 的 tag**，否则 cycle 挑不到它。
4. 在 `spec.md` 中写清范围（一个度量，或一批同域的债）与完成判定（读数回到阈值以下，或该批条目全部进入终态）。
5. 若 `doctor` 清单中没有识别该类债的插件（或插件未安装），则按普通节点编写，**禁止自行编造方法名**。普通节点不写 `method:`。

## 落笔前自检

- **交接测试**：把 `intention.md` 与 `spec.md` 交给一个没参加过本轮讨论的人、只给他仓库——他能否不靠猜就做出你心里「过」的成品？他不得不靠猜补全的东西（参照路径、目标形态、换新还是沿用），就是 `spec.md` 缺的东西；他自己读代码就能查到的（函数名、行号、实现步骤），一律不写。
- **判据对齐测试**：若 `spec.md` 里的完成判定全绿，成品是否还有可能让你一眼判定「不对」？若是，说明判据用了机械替代指标，补回与真实判断方式一致的对照或检查。
- **基础项**：`intention.md` 只描述目标与原则、能回答「为什么」、不含当下盘面现状；`spec.md` 落点唯一、无函数名/实现步骤、尺寸贴合完整交付单元；有否决方案则附「不做的事」；清债节点附 `method:` 与范围。
