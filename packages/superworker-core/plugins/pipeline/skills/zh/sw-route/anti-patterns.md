# sw-route 常见反模式

执行前对照检查。完整判据见 [`./SKILL.md`](./SKILL.md)，本文件仅列出症状、纠正信号与示例。

## `route-edits-project-files-directly` · 绕过管线直接修改项目文件

**症状**：在需求讨论阶段，Agent 直接编辑或写入了工程代码与业务文档。

**纠正信号**：用户反馈「我没让你改代码」。

## `route-advances-without-reading-graph-or-docs` · 未读图与项目文档即推进讨论

**症状**：收到用户想法后，Agent 既未读取 DAG 也未查阅项目文档，直接开始讨论方案或起草节点。

**纠正信号**：用户反馈「这个节点已经有了」「这和之前的设计冲突」。

## `route-dumps-raw-data-at-user` · 向用户倾倒未经提炼的原始数据

**症状**：用户询问图里目前有哪些内容，Agent 直接把整段节点 JSON 原样输出。

**纠正信号**：用户反馈「信息太多」「说重点」。

## `route-node-name-depends-on-source-context` · 节点命名依赖来源文档上下文

**症状**：节点名使用了「方向 5」「方向 1」等依赖外部文档编号或章节位置的指代。

**纠正信号**：用户反馈「看不懂这个名字」「名称应该自描述」。

## `route-creates-orphan-node` · 新建节点未声明下游依赖，成为孤点

**症状**：新建节点只加了上游依赖（该节点依赖谁），未加下游依赖（谁依赖该节点）。孤点不在任何推荐路径上，其 urgency 和 importance 均为 0，实质上被排除在管线之外。

**纠正信号**：列图时该节点未出现在任何推荐路径中。

## `route-deletes-node-or-edge-without-impact-check` · 未核对影响面即删除节点或依赖边

**症状**：用户提出删除节点时，Agent 直接强制删除；或未检查上下游关系就移除依赖边。前置依赖静默消失后，下游节点会在错误前提下运行，且图上不再留有缺失痕迹。

**纠正信号**：用户反馈「为什么断了这条边」「谁让你删的」。

## `route-splits-without-verification-boundary` · 节点拆分未以独立验证边界为依据

**症状**：提出的拆分方案无法对应独立的验证标准：要么多个节点共用同一套验证（拆得过细），要么单个节点混杂了多种验证方式（拆得过粗）。

**纠正信号**：用户反馈「这两个应该合在一起做」「没必要拆这么细」。

## `route-spec-has-implementation-detail-or-no-done-check` · spec 写入实现细节，或缺少可执行的完成判定

**症状**：spec 中写入了函数名、行号、调用顺序或具体实现步骤（文件夹与文件名作为改动落点允许写入）；或者通篇只有「做 X 的设计」「调整 Y」这类宽泛表述，缺少能跑出明确通过/失败结果的验收口径。

**纠正信号**：`sw-conduct` 准备阶段中止，并报告「完成判定无法执行」或「spec 与代码前提不成立」。

## `route-spec-scope-unpinned` · spec 未钉住改动范围

**症状**：spec 只写了要做什么，没写明改动的具体落点；或者写了落点，但该表述在项目中有多处指代。

**纠正信号**：落笔前拿 spec 自检「改动落在哪儿」，若答案不止一处，说明范围尚未收口。

**示例**：

    这个命令的输出太乱了，收拾一下，注意别影响别的地方。

既看不出改在哪里，也无法判断是否完成。规范写法：

    目标：统一该命令输出三列的列宽。
    范围：该命令自身的入口，不含下游子命令。
    判据：执行一次命令，三列按最长项对齐；参数解析与退出码保持不变。

## `route-lowers-parallel-instead-of-adding-edges` · 用调低 parallel 替代声明依赖边

**症状**：发现多个节点会修改同一批文件时，直接将 cycle 的 `parallel` 调小甚至设为 1，理由通常是「为了安全」「防止冲突」。

**纠正信号**：用户反馈「会冲突就加依赖边，不要降并行度」「别拿 parallel 凑合」。

## `route-writes-node-before-requirements-settle` · 需求尚未收敛即落节点与 spec

**症状**：用户还在讨论设计、关键取舍尚未敲定，Agent 未先摆出方案确认，就直接将讨论压缩成结论并建节点、写 spec。

**纠正信号**：用户反馈「你推进太快了」「先停下来把方案聊清楚」「把刚才加的节点删掉」。

## `route-creates-discussion-or-acceptance-node` · 将讨论或总验收建为 DAG 节点

**症状**：图中出现「与用户讨论 X 的设计」「全部完成后进行实机测试／联调／验收」这类节点。

**纠正信号**：用户反馈「这种节点不用建」「这个我自己测就行」。

## `route-reads-a-landed-line-as-a-started-node` · 将已落盘的 cycle 误报为节点已在运行

**症状**：执行 `cycle start` 或 `cycle status <id> active` 后，Agent 报告「cycle 已开启」「第一枚节点已就绪」，把 `cycle current` 中的 `Node:` 行当成正在执行的信号；但实际并未拉起任何执行会话，用户「启动这个节点」的要求只完成了一半。

**纠正信号**：用户追问「它跑起来了吗」「现在谁在跑」。

## `route-hands-over-a-command-without-pipeline` · 交接启动命令时遗漏 `[pipeline]`

**症状**：交付的启动命令写成 `/sw-conduct <node-id>`，漏掉了 `[pipeline]` 标记。用户执行后只跑完这一枚节点便停止，收尾、提交推送与下一枚推进均未接续，整条 cycle 停在原地。

**纠正信号**：该会话做完一枚节点即结束，`cycle current` 显示管线仍停在原处。
