# Conduct: State and Advancement Contract

> Architectural design reference for `conduct`: the execution line model, the single state writer, and intentional design trade-offs.
> Command syntax, field schemas, and output formats are not duplicated here—refer to `--help`, `plan --help`, and the source code.
> For conductor operations, see [`../SKILL.md`](../SKILL.md); for dispatch, see [`conduct-dsh-dispatch.md`](conduct-dsh-dispatch.md); for node tags and cycle routing, see [`conduct-node-tags.md`](conduct-node-tags.md).
>
> Agents do not read this file at runtime—conductors read and write state exclusively through the engine CLI and never edit JSON directly.

## 0. Pipeline Model

A **cycle** is an execution line: it advances DAG nodes (one held at a time by default), dispatches each node to an isolated session, records the outcome when the session reports back, and then selects the next node—or stops.

```
cycle -> node -> (session's prepare / execute / review / fix) -> next node or stop
```

How work is organized inside a node is private to that session; the pipeline neither observes it nor records it in `.superworker/`. The pipeline ledger tracks only three things: the cycle's identity, the node(s) it currently holds, and the path it has walked.

The pipeline itself inserts only one kind of node into the DAG: a maintenance node requested by a plugin registered at the **close** timing. **Insertion mutates the graph only**—it creates the node, wires the edge, and writes its spec without launching a session or altering the cycle's current holdings. The inserted node is wired directly ahead of the node this close would have opened next, so ordinary ranking picks it first on the next selection without special pinning. All other nodes are created exclusively by `sw-route` with user confirmation.

## 1. Three Roles

| Role | Owner | Authority |
|---|---|---|
| Execute | `sw-conduct` | Performs work and reports facts only. **Can run standalone**; orchestrates its own subagents internally |
| Record & decide | Engine CLI (`packages/superworker-core/src/conductor.ts`) | **The sole state writer**. Computes every rule-based decision deterministically |
| Approve | User | Handles only non-computable decisions: confirming intent and deciding when to pause or resume |

**Any decision expressible as a deterministic rule should not spend another model session re-evaluating it.** Sessions contribute only what they uniquely observe (execution outcomes and measured readings); everything computable (next node selection, maintenance insertion, threshold checks, stop conditions) lives in the engine.

## 2. State: One Cycle, One Record

A cycle's identity, current holdings, and execution history all reside in a single cycle record, with no secondary pointer file to keep in sync. All state mutations must go through the engine CLI; hand-editing forks from the engine's view and breaks subsequent conductors. File layout and git tracking under `.superworker/` are governed by the `.superworker/AGENTS.md` generated by `init` and the repository's git config files.

Key design choices:

- **Claims live in `holding`**: A node may be held by at most one cycle at a time. Being in flight does not change the node's graph status—the node remains `todo`, while ownership is a property of the cycle. Two distinct facts occupy two separate fields.
- **Ownership is recorded at pin time (`hold`)**, not when the session reports back—so mid-run graph edits cannot redirect an active step.
- **Full path history is append-only**: Retrying a node appends a new step and verdict; readers inspect the latest entry while history explains how the cycle reached its current state.
- **Verdicts and node statuses are separate vocabularies**: Sessions write a verdict on the handoff ticket (delivered or not); graph nodes have only "in play / shelved waiting / completed." A ticket on disk means only close-out remains. A retry marker is **always treated as a red light**—while present, downstream readers wait.
- **Only one class of metric is requested from sessions**: Ticket fields are stored verbatim without validation, except for readings declared by a plugin whose bound configuration knob has an active value on the resolution chain (either configured on a layer or given a factory default; see Section 9). Metrics computed directly by plugin tools never travel through tickets and are never requested from sessions. **The reporter does not decide; the decider does not measure.**
- **Derived states are never persisted**: Labels such as "ready" and "running" are computed at read time.

## 3. Session Launch, Context Injection, and Close Ordering

**The launch prompt contains only one invocation line**: the session reads the node title, spec path, and close commands on its own, and user instructions are injected dynamically by the host with each turn's context (zero bytes if none are visible or `injectInstructions` is disabled). Embedding dynamic context into a static prompt only creates stale duplicates.

**User instructions are injected dynamically by position**: Every session (conductor and dispatched subagents) receives the exact list that `instruction list` would print from its current position. When nothing is visible, the CLI prints a "no instructions" message while the host injects zero bytes; disabling `injectInstructions` (enabled by default) also injects zero bytes.
- **Position scoping**: Instructions exist at two levels only (`global` and `cycle`). A session's position is its dispatch claim — the `run` note naming it, and the node its line holds. Cycle-bound instructions reach exactly the sessions working that line's nodes; instructions bound to another cycle are neither injected nor enforced at close-out. Creating a node (the birth note) or discussing it claims nothing.
- **No position, no line's rules**: A session the record cannot place (a consult, a hand-opened session) reads the globals alone, and only once it has actually run a verb of its own — a session that has never touched the pipeline carries not one byte. A line's working rule is nobody else's business, and silence costs the outside reader nothing. Visibility is purely derived and never persisted, so no cleanup is needed when a scope ends.

**Only the user modifies the instruction list**: Archiving retains an entry while stopping injection; deleting removes the body and leaves an ID + timestamp tombstone for cross-machine merging—preventing a pull from another machine from resurrecting deleted items or reusing IDs. Tombstones are hidden from human views and do not constitute a third status. Unarchiving is also user-only; sessions never add, remove, or toggle instructions.

**Close-out order is strictly fixed**: After `handoff` (writes the ticket) and `settle` (closes the node), the required sequence is **`git commit` → `git push` → `advance`**. The next session boots in the same working tree and pulls first; an uncommitted tree causes pull failures or partial reads. Therefore **advancing the cycle is always the final step**. `settle` itself never pins nodes or launches sessions—on threshold breach it only inserts maintenance nodes ahead of the next candidate, leaving pinning and dispatch to `advance`. Splitting `handoff` and `settle` also makes the intermediate state ("ticket on disk, node not yet settled") stable and inspectable if the chain breaks midway.

**Filing a ticket drives nothing**: Writing the handoff ticket simply leaves the node waiting for `settle <node>`. `settle` closes the node; `advance` pins the next node, materializes its prompt, and opens the session. Only the dispatch chain writes launch prompts—`handoff` never touches them.

**Old sessions are never resumed**: Every node starts in a fresh session so prior conversation context never bleeds across nodes.

**Tools execute mutations; sessions read `action` only**: Returned actions never carry shell command strings to execute. Write endpoints succeed only when they genuinely mutate the pointer, ticket, path, or cycle state, and throw otherwise. External probes are bounded by timeouts—for example, `doctor` marks a git check red with elapsed wait time rather than hanging indefinitely.

## 4. Settlement vs. Advancement Entry Points

`settle <node>` closes a single node; `plan` previews the next action; `advance` is a composite verb that sequentially pins (`hold`), materializes launch files, and opens sessions (`dispatch`). The standard flow can also run `plan` → `hold <node> --cycle <id>` → `dispatch <id>` step by step.

- **`settle` records only**: It logs the step, updates node status, and runs close-time plugins without pinning a next node or opening a session.
- **`worktree_mode` does not alter settlement's disk-only checks**: `worktree_mode` accepts `off` or `fork` (defaulting to `fork` in git repos and `off` elsewhere, overridable at project or global layer; see Section 8). `reuse` is rejected immediately (`worktree_mode_unsupported`). Sessions run git commands to create, merge, and remove worktrees; the engine owns only records and naming, so `settle` never inspects worktrees.
- **`advance` enforces derived stop gates**: If the last step is an unapproved `checkpoint`, a still-`shelved` node under `when_shelved=stop`, or `path.length >= stop_after_nodes`, `advance` pins nothing and returns `stop_pipeline` with the clearing command.

**No writable cycle status bit**: Cycle records carry no `active / inactive` toggle and no persisted default-cycle pointer. Whether a cycle is `running` (holding nodes), `waiting` (stopped at an unapproved checkpoint or shelved stop), or `idle` is derived live from `holding`, `path`, and graph node states.

Aligning the target cycle during `sw-route` ensures `/sw-conduct` starts against an explicit cycle without guessing.

## 5. Verdicts and Stop Conditions

- **Delivery is decided by the ticket on disk**: The engine updates node status from the handoff ticket without consulting another session. The ticket holds the coarse verdict; detailed findings stay in session reports.
- **Post-non-delivery behavior follows cycle policy**: `when_shelved` determines whether the cycle pauses for the user or advances past a shelved node. Under either setting, the undelivered node itself is shelved waiting for human attention.
- **Stop points follow node `mode` first**: `auto` has no human gate; `manual` confirms within the session; `checkpoint` pauses immediately after close-out for the user to approve. Cycle `stop_after_nodes` can only add stricter stop points on top of `mode`, never relax it.
- **Human approval is persisted per delivery on the node**: `checkpoint` gates are evaluated live from `approved_at >= completed_at` on the node itself; `dag approve <node>` is the sole write entry point. Approval is **per delivery, not per node**: a subsequent re-delivery moves the delivery timestamp past the old approval, invalidating it automatically with no manual revocation or secondary ledger.
- **Derived 3-state view, never stored**: A cycle reads as `running` (holding nodes), `waiting` (stopped at a human gate), or `idle` (everything else)—derived on read since the DAG can grow at any time.
- **One canonical ranking**: The engine pulls full rankings from the DAG layer and filters rows by readiness and cycle tags without re-implementing scoring, preventing ranking drift.

## 6. Core Invariants

Each invariant below prevented a real production bug:

1. A terminal handoff ticket is the sole authority that a node is done; retry markers always read red and require rolling back the ticket before replacement.
2. "Ticket filed, not yet settled" is a **stable state**: repeated queries return the same wait message and `settle` command while writing zero bytes.
3. Closing one node never closes the entire cycle: sibling nodes in the cycle continue on their own close-out lifecycles.
4. `stop_after_nodes` can only add stop points on top of node `mode`, never weaken it.
5. Each tool reads only its own ledger (the DAG layer does not read cycle records); combining both records to see "who is running what" belongs to readers that inspect both.

## 7. Recovery

**Unified retry path**: Roll back the ticket via `cycle retry <cycle> <node>` (add `--drop` if the session died while `started` remains on disk to clear the claim too), return the node to ready, re-pin with `hold`, and run `advance`. Verdicts append sequentially—the engine checks only current ownership.

**Broken chains fail loudly**: Calling `settle` without a ticket fails immediately with `nothing_to_settle`; dispatch failures propagate their exact reason (shown in the panel UI or logged by auto-relay). `started` is the sole proof that a session opened: if absent, `plan` treats the cell as dispatchable; if present for a dead session, clear it first with `cycle retry <cycle> <node> --drop`, then re-hold and `advance`—never force a duplicate dispatch.

**No resident watchdog by design**: A watchdog would require maintaining a background daemon. If a session hangs without writing a ticket, no automatic detection fires; the cycle waits quietly at that node until a human recovers it via `/sw-conduct`.

## 8. Settings: Five-Layer Resolution Chain

**Every setting is a typed knob**: `number`, `integer`, `word`, or `switch`. Knobs come from two sources—core built-ins and installed plugin declarations—merged into one table with single ownership per name. **Core settings and plugin knobs use the resolution chain; a cycle's four execution policies do not** (see last bullet).

- **Five layers (narrow overrides wide)**: node → cycle → project → global (machine) → factory default. Resolution is fully deterministic.
- **Layer eligibility (`layers`)**: Not every knob is valid on every layer. Core settings (`max_agents`, `test_tier`, `worktree_mode`) apply only to project and global layers. Plugin knobs allow all four writable layers by default unless narrowed in their declaration. A knob hand-written into a disallowed config file is flagged by name and skipped on read—unreadable values never sit silently on disk.
- **Reads report value and provenance**: Every lookup knows both the effective value and its source layer, answering "why didn't my setting take effect?" `config list` displays both; `config get` prints only the value for skill scripts.
- **Two write commands**: `config set` writes to exactly one layer; `config unset` removes that layer's entry so wider layers show through. Writing to a disallowed layer fails and lists permitted layers. For switches, `off` is an explicit value, whereas `unset` removes the override. Omitting a layer flag targets the project layer; cycle-layer knobs are persisted on the cycle record by its sole writer.
- **Strict parse errors**: An unparseable value in a file layer exits with an error instead of silently falling back to factory defaults. The lone exception is the cycle layer, which is read leniently as a state record (invalid values treated as unset).
- **Optional factory defaults**: Plugin thresholds may omit `default` (reading as `-` / unconfigured until set on some layer) or define a `default` (active immediately on install, prompting the ticket form to request the corresponding reading). Evaluation and form prompts read the same source.
- **Four cycle policies are line-layer knobs**: `parallel` (max concurrent held nodes), `when_shelved` (stop or continue on non-delivery), `stop_after_nodes` (stop after N closed nodes), and `model` (`provider/model` route for launched sessions) live in the `policies` slot of the cycle record and take the line layer only — `config set <key> <value> --cycle <cycle>` writes, `config get <key> --cycle <cycle>` reads, `config unset <key> --cycle <cycle>` clears; the project and global layers do not take these four names. `config list --cycle <cycle>` lists every knob that line can see (the issue-pool and test-time line overrides included) with its source layer in one go.

## 9. Plugins and the Maintenance Channel

**A plugin is a directory**: `plugins/<name>/` holds three parts:
1. **Declaration (`plugin.json`)**: Pure data declaring timing, registered knobs and readings, action type, dedupe tag, and method skill names.
2. **Implementation (`impl.mjs`)**: Executable code invoked at the declared timing, plus any helper files listed in `files`.
3. **Bundled skills (`skills/<lang>/<method>/`)**: Installed by `installPluginSkills` in `src/host/skills.ts` by copying each method folder for the host's language into `<dshHome>/skills/<method>/` and recording the manifest at `<dshHome>/superworker/skills.json` so skills install and uninstall alongside the plugin.

The folder name is the plugin's identity: delete it to uninstall, restore it to reinstall, with zero core code changes.

**Core validates closed types, never hardcoded names**: The closed set comprises the four knob types, two timings (`close` / `dispatch`), and two actions (`insert` / `block`). Only two combinations are valid: **insert at `close`, block at `dispatch`**—any other combination is skipped at runtime and flagged by `doctor`. The registry (`packages/superworker-core/src/plugins/registry.ts`) enforces uniqueness across knobs, readings, reading sources, dedupe tags, method names, and skill names—no cross-plugin sharing or borrowing is allowed. Because declarations are pure data, listing plugins or rendering help never executes implementation code, ensuring one broken plugin cannot break help or diagnostics.

**Exclusive reading sources**: A reading comes either from a session report or a tool computation. The core defines one built-in source; plugins measuring custom metrics claim their own source name in `plugin.json` and point to a function in `impl.mjs`. Core passes values through without interpreting them, treating wrong types as "unknown this run." Source names are exclusive to the claiming plugin and cannot be borrowed by another plugin—unauthorized references fail `doctor` and are skipped at runtime without halting the pipeline.

**Command word registration**: Declarations may also bind CLI command words (`<word> ...`), routing invocations to `main` in `impl.mjs`. Command-only plugins need not declare a pipeline timing or action; plugins with no command words must declare both. Command ownership, help entries, and collision resolution appear in `doctor`.

**Close-time insertion**: `settle` invokes all `close`-timing plugins; each triggered plugin contributes at most one node per close (multiple breached metrics insert multiple sibling nodes). Inserted nodes are wired ahead of the next candidate so normal ranking selects them first. **A plugin that wants the cycle to keep advancing must stop triggering while its maintenance node is still open** (typically via dedupe tags)—the core does not guess this on the plugin's behalf.

**Tolerant at runtime, strict in `doctor`**:
- **Runtime**: Unreadable declarations are skipped silently. Load failures, thrown errors, or `process.exit` in implementations attach a `WARNING:` payload to the close/dispatch return value for the caller to display, without blocking other plugins or the active pipeline.
- **Validation (`doctor` and test suite share one validator)**: Strictly checks closed-set compliance, cross-plugin name collisions (including reading sources and skill names), implementation loadability, existence of declared source functions (presence check only, no live call), local ownership of referenced method skills (unreferenced standalone user skills are valid), and runs one dry call against a mock project verifying no throws and no direct graph edits. Validation never runs on the hot pipeline path.

**Enable/disable via `switch` knobs**: Follows the five-layer chain in Section 8; plugins without a switch stay always on. The host's `enabled()` check skips disabled or unreadable (`off`) plugins before invoking them, so implementations need not track their own enabled state.

**Dispatch-time blocking gate**: A `dispatch`-timing plugin may refuse launch with reasons recorded in `dispatch_blocked` while keeping the cycle `active` (ideal for rate-limit or time-window gates). The gate must be **cheap, idempotent, and read-only**, invoked by `conductor.dispatch` after reading `started` and before writing prompts or opening sessions—a blocked dispatch writes no prompt, opens no session, and leaves the pinned node intact for the next attempt. Gates must never count calls, write to disk, or change answers on repeated identical checks.

### Maintenance Channel

**Each maintenance debt corresponds to one metric in a plugin declaration.** At close-out, a `close`-timing plugin checks whether its metric meets or exceeds the configured threshold (defined as the maximum acceptable value; `reading >= threshold` breaches) and requests a maintenance node when breached. **Each debt is self-contained**: data source, evaluation logic, spec template, and payoff criteria belong entirely to its owning plugin.

- **Project-level debt entry point**: Maintenance work has no business dependency edges and would otherwise sink to the bottom of the DAG ranking. The channel injects it at close-out according to the cycle's configured thresholds.
- **Independent evaluation**: Switches, thresholds, dedupe tags, and method names are private per plugin (inspectable via `doctor`). Multiple simultaneous breaches insert one node per breached plugin.
- **Decisions stay in the engine**: Close-out evaluates the handoff ticket and graph snapshot; sessions report only raw readings and never decide whether maintenance is due.
- **Zero-config regression floor**: Unconfigured thresholds stay inactive with byte-identical close output; plugins switched `off` neither insert nodes nor request readings.
- **Priority via graph edges, not ranking hacks**: Inserted nodes add one edge (`maintenance node → next scheduled node`), letting standard DAG scoring promote them to the front without changing ranking code.
- **Sibling insertions**: Multiple maintenance nodes inserted during the same close all point to the same successor node with no ordering between them.
- **Inherited cycle tags**: Inserted nodes receive the current cycle's tags so they remain visible within that cycle's selection filter.
- **Deduplication**: Dedupe tags ensure at most one open maintenance node per metric exists in the graph at a time; subsequent breaches wait until it closes.
- **Standardized generated specs**: Generated specs follow normal node conventions—a one-sentence scope (bring this metric back within threshold), a runnable done criterion, the trigger context (metric name, reading, and threshold), and the method skill directive. Templates never guess implementation details (no function names, file paths, or line numbers); work that cannot be expressed as a runnable criterion stays out of the maintenance channel.
