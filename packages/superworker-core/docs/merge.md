# 合并驱动

两台机器各跑一条流水线、各有一份 `.superworker` 记录，合回一处时四份记录各有领域判据，认不出名字的
记录按形状、按条目求并，都不按行：合并落在解析后的记录上，结果用与记录写入者同一把写尺写出（同一套
缩进、排序键与换行），判断与字节同出一处。驱动是内部模块（`src/ledgermerge/`），不进包出口，也没有命令面。
它有一个进程入口 `sw-merge-ledger`——git 的合并驱动只能靠进程叫（这个包的进程面只有这一条，见
[api.md](api.md)）。

## 接上 git

git 那一侧由 `init` / `register` 接上：`.superworker/.gitattributes` 是 `init` 落下的布局文件（不经 git
命令），写进项目 git 配置的两个键才走 git 自己的命令；git 的目录布局引擎不碰：

- `.superworker/.gitattributes` 把记录树下的记录 JSON 都标成 `merge=superworker`（`** -text` 顺带把行尾钉在
  记录的 LF 上），布局里那份设置文件显式退出（`config.json -merge`）；
- 项目 git 配置里两个键，都走 `git config --local`：`merge.superworker.name`（git 给人看的标签
  `superworker ledger three-way merge`）与 `merge.superworker.driver`（命令串）。写之前先读一遍：本机真答得上的注册
  一个字节都不改写，没有注册、或注册已经答不上时才写——重跑因此幂等；
- 命令串只有一种写法，写的时候现算：绝对形式
  `"<node 可执行文件的绝对路径>" "<本包 merge-ledger.mjs 的绝对路径>" %O %A %B %P`。两条路径都带
  引号（Windows 的 node 路径里有空格，git 按空格切这条命令串），末尾是 git 自己的参数。不探测
  `PATH`：绝对路径只指向发布件里自己的文件，不回到仓、也不要 `node_modules`，装到哪儿都答得起来。

回答那条命令的就是 `sw-merge-ledger` 这一个进程：它把 git 给的四个参数（`%O` 公共侧、`%A` 这一侧、
`%B` 另一侧、`%P` 记录在仓库里的路径）搬进来，把合并交给 `runMergeDriver`，再把退出码原样交出去。
`--dry-run` 出现在参数里的任何位置都只打判词、一个字节都不写。stdout / stderr 按 UTF-8 写。

## 范围

四条领域判据各管一份记录：图（`ideas.json`，节点）、线（`state.json`）、指令（`instructions.json`）、
交接单（`signals/<线>/<节点>.json`，整个文件就是一条记录）。认哪份记录先看名字（`%P` 先，然后是
`%O` / `%A` / `%B` 三个路径），名字认不出时看内容的形状：带 `nodes` / `cycles` / `instructions`
集合键的那三份，或有 `status`、并且带 `timestamp` 或 `outputs`、底下没有集合的交接单；再认不出，只要
它有一个集合键、键下是一组每项带自己 `id` 的条目（一串，或按 id 做键的表；空集合不算，三侧说出的
键名不是同一个也不算——都见下一节），就交给下面那条按条目求并的通用规则（插件的记录长成这个形状时也落在
这一层——问题池 `issues.json` 就是这种表：`issues` 键下按 id 做键、每项带自己的 `id`）。一样都认不出
的文件原样退回（退出码 2），不猜。

## 记录树在哪

git 在**工作树的顶层**拉起驱动，项目可能在那下面好几层，一个 checkout 里也可能有好几个项目，
所以驱动不假设记录树就在身边。记录树也只在真要写盘时才找：并出来的结果与 `%A` 逐字节相同，
驱动直接退 0，一个位置都不找。要找时三步：

1. 有 `%P` 时，取它里面 `.superworker` 那一段前面的目录，接到驱动的工作目录上——那个位置得有一份
   **init 过的** `.superworker` 才算数（`%P` 指到一棵没有记录树的树，或指到没 init 过的记录目录，都算
   没找到）；项目在仓库子目录里、一个 checkout 里有多个项目，都靠这一步认对位置；
2. `%P` 缺席、或它里面没有 `.superworker` 段时，从工作目录往上走，走到最近那份 init 过的 `.superworker` 为止；
3. 两处都没有，就明说 `no .superworker sits at …`（位置也印出来）：不替人判一场它放不对位置的合并。
   `%P` 带 `.superworker` 段、那个位置却没 init 过时也落在这一步：位置是 git 点名的，不再往上走——
   去别处找一棵记录树来判，等于在一处 git 没点名的地方下判决。

## 判据

一条记录只在两侧把同一个字段改成两个不同值时才成为问题：两侧一样就取它，只有一侧改过就取改过
的那一侧；两侧都改过才轮到下面这些规则，规则定不下来就是冲突。

- **图**：节点按 uuid 取并集。`status` 两侧都挪了就取更高的一档（`todo` < `shelved` <
  `completed`），词汇表以外的词是冲突。依赖边两侧都只加边就取并集，任一侧剪过边（或没有共同
  祖先可比）就是冲突。`title` / `description` / `mode` / `tags` 由 `updated_at` 判后写的那次赢；
  `updated_at` 取晚的、`created_at` 取早的。取下节点会传播：一侧取下、另一侧原封不动就是删除，
  一侧取下、另一侧改过是删 vs 改的冲突。合并弄断的依赖边要点名——`ledger.dag.validate` 会报悬空
  引用，在那之前这条边读作已满足（节点显示就绪）。
- **线**：条目从不被删（工具里没有删线的命令），只有一侧有的条目就是「这一侧从来没有过」。
  `path` 只追加：一侧是另一侧的前缀就取长的，两条不同的尾巴按走过的时刻并起来；同一个节点两侧
  记了不同判决是冲突。`status` 只有 `active` / `inactive`，两侧各说一个词就是冲突。
- **指令**：条目像图一样传播删除；摘下留下的痕迹（`removed` 表，只有 id 与时刻）按 id 取并集、
  从不收回，时刻取早的那个。`state` 与 `resolved_at` 成组裁：只有一侧改过取那一侧，两侧都改过
  按 `resolved_at` 排，新的那次行动整组赢；一侧放回（清掉了时刻）、另一侧又改过，是两个主人
  行动撞在一起，冲突。两侧都改过的 `note` 是冲突：人写的一句话不悄悄覆盖。
- **交接单**：终局词（`completed` / `failed` / `stopped`）压过未终局的词（`pending` 是重跑留下
  的记号），不论时刻怎么说；其余字段两侧都改过时，取带更晚 `timestamp` 的那张票——记录自己写下
  的时刻，是唯一跟这两次尝试有关的次序（驱动拿到的是 git 自己的临时文件，它的修改时间只说 git
  什么时候写了那个文件）。两张票排不出先后（一侧没有 `timestamp`，或两侧是同一个值）就是冲突：
  不抛硬币，交给人。

## 认得出形状但没有名字的记录

驱动不认识这些记录的领域，只认得出一种形状：一个集合键，键下是一组条目，每项都带自己的 `id`。两种写法
都算这个形状——一串条目，或按 id 做键的表（键与条目自己的 `id` 是同一个身份；对不上就是一行两个名字，
驱动认不出，原样退回）。认得就按条目自己的 `id` 把两侧求并：

- 只有一侧有的条目整个取过来。驱动没有「这条被删了」的证据——那是记录主人的命令——所以它不传播
  删除：一侧删、另一侧没动，条目留在结果里，谁的活都没丢。
- 同一个 id 两侧都有，就逐字段判：两侧一样取它，只有一侧改过取改过的那一侧，两侧改成两个不同的值
  才是一条冲突。判词照旧点明哪份记录、哪一条、哪个字段、两侧各是什么。
- 它不做领域判断：不认时刻（不排「谁后写」）、不认状态词表、不解释字段是什么意思。所以两台机器各
  改了同一条记录时，它把两侧的原话一起交到人手上，由人来挑。

**不管什么**：空集合不算这个形状——这一侧没有一条带 `id` 的条目，就谈不上「每项带自己的 `id`」；
三侧（公共侧、这一侧、另一侧）都拿不出条目时（`{"version":1,"issues":{}}`），文件里没有一处说得清
它算不算一张按 id 的表，原样退回（退出码 2），不猜。空的那一侧本身不碍事：另有一侧在同一个键下给出
条目时，这次合并照常按那个键求并，空侧只是没带条目。三侧说出的集合键对不上时也一样：一份文件自己
说了两个身份（这一侧的表叫 `items`、另一侧的叫 `rows`），驱动不替它挑一边，原样退回（退出码 2），
一个字节都不写，判词点名每一侧各是哪个键——挑一边的后果是另一侧整张表被当成普通字段带过来（或这
一侧的条目整个丢掉），留下一份驱动自己下次也不认的记录。

形状与字节都照旧：这侧是一串就落成一串，这侧是按 id 做键的表就落成表；字节按记录写者那把尺写（两空格
缩进、LF、无末尾换行），键序不重排。这份记录的拥有者是谁驱动并不知道，重排键序、改掉集合的写法都是在
替它表态。

**设置文件为什么退出**：记录树下的记录 JSON 都由 `.superworker/.gitattributes` 的一条模式行交给驱动，
只有布局自己那份 `config.json` 显式退出（`config.json -merge`）——它只是一份设置文件，装的是这个目录
自己的几项设置，没有一张条目表可以按 id 求并。`-merge` 的意思是这份文件不交给任何合并驱动、由 git
自己处理：在这份 `.gitattributes` 的 `** -text` 之下，两侧都改过的设置就是一处二进制式冲突，这一侧的
字节原样留着、由人判。

插件可以在声明里写下自己记录的合并策略（`plugin.json` 的 `merge.strategy`，今天只收 `by-entry`），
但驱动不装载插件：合并是一次进程调用，没有插件目录的解析上下文，执行走的就是上面这条通用规则。

## 出口

| 退出码 | 意思 |
| --- | --- |
| 0 | 并好了：结果已写进 `%A`，或与它逐字节相同、不必写 |
| 1 | 要人判（或记录树的锁一直没空出来）：一个字节都没写，git 留着 `%A`、把这次合并记成冲突 |
| 2 | 用法或读盘错误：认不出是哪份记录、形状不对、解析不动、没有记录树，或者有一侧读不动 |

记录树是驱动自己找的。调用方直接点名 `root` 跑 `runMergeDriver` 时，那份记录树没 init
过读作 1——位置对，只是还没准备好。

缺席只有两种：文件根本不在，或 git 的 add/add 交来一个 0 字节的文件（读作「这一侧没有记录」，
并且明说出来）。一侧在那儿却读不动——共享锁、没权限、该是文件的地方是个目录——算用法错误
（退出码 2），一个字节都不写：把它读作缺席，就会拿另一侧的记录盖掉它，让 git 以为这次合并干净
了。只有一侧有这份文件时，它整份就是结果。

冲突逐条落在字段上——哪份记录、哪个条目、哪个字段、两侧各是什么——一条一行进 stderr；冲突时
一个字节都不落，人先按判词手工合，再 `git add`。`--dry-run` 只把判词打出来，一个字节都不写：
决定进 stdout、冲突进 stderr。写入持记录树的锁，整份记录与别的写入者互斥。
