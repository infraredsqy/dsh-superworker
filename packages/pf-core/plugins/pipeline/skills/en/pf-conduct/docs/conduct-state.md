# conduct: state and the contract of advancing

> This is conduct's **design source**: how the execution line is meant to work, who the one writer is, and which decisions were made on purpose.
> The words, the fields and the shape of a line are not copied a second time here — those follow `--help` / `next --help` and the code.
> The operating manual a conductor reads is this same skill ([`../SKILL.md`](../SKILL.md)), derived from this document;
> dispatch and authentication are in `conduct-dsh-dispatch.md`, tags and routing in
> `conduct-node-tags.md` — both sit in the same `docs/` folder of the conduct skill.
>
> The agent does not read this at run time — a conductor reads and writes state through the words layer alone, and never touches the JSON.

## 0. What a pipeline is

A **cycle** is one execution line: it carries DAG nodes forward (one at a time by default), hands one to a session, records that step when the session reports back, and then picks the next — or stops.

```
cycle -> node -> (the session's own prepare / execute / review / fix) -> the next node, or stop
```

How the work is split inside a node is that session's own business; the pipeline cannot see it and writes none of it into `.pf/`. The pipeline's own record keeps three things: the cycle's identity, the node it holds right now, and the path it has walked.

The pipeline itself puts exactly one kind of node into the graph: the one a plugin declaring the **close** timing asks for. **An insertion only edits the graph** — it sets the node up, wires the edge, writes its spec; it opens no session and does not move the line's hand. The inserted node hangs behind the node just closed, and who runs next is settled by the picking step that follows under the ordinary rules: nothing is pinned. Every other node is still drawn by pf-route, which comes back to the user to do it.

## 1. Three roles

| Role | Who it is | The little power it holds |
|---|---|---|
| Doing the work | `pf-conduct` | does the work and hands back facts only. **It can run on its own**; it directs its subagents itself |
| Writing it down | the words layer (`packages/pf-core/src/conductor.ts`) | **the one side that may write state**. Every judgement that can be computed is computed here |
| Judging | the human | only what cannot be computed: reading his own words, deciding whether to stop now |

**A judgement that can be written as a rule should not cost another session to make again.** That one sentence settles the whole division of labour: a session hands over only what it alone has (the conclusions of the work, the readings only it can take), and everything the tool can compute (who is picked, how many nodes are added, whether debt is due, whether to stop) is never judged inside a session.

## 2. State: one line, one record

Identity, the node held right now and the path walked all live on that one cycle record, with no second pointer file to keep in step — state goes through the words layer alone, and editing it by hand forks from the tool, so the next conductor follows the wrong copy. Where things live under `.pf/`, and which of them go into the repository, is settled by the `.pf/AGENTS.md` that `init` writes and by the two git config files.

A few decisions made on purpose:

- **A claim is written onto `holding`.** A node may be held by one line only; being worked on does not change the node's status — the node itself stays `todo`, and who is working it is the line's property. Two facts, two fields, neither explaining the other.
- **Ownership is recorded the moment the node is pinned**, not when the session reports back — so editing the graph mid-run cannot bend this step.
- **Every step of the path stays.** A node redone is two steps, and verdicts are appended one by one; a reader reads the latest, and the history explains how it got here.
- **Verdicts and statuses are two vocabularies.** A session writes a verdict on the ticket (delivered or not); a node on the graph is only "in play / out of play waiting / done". A ticket on disk means this node has only its close left; the mark a retry leaves is **always read as red** — leave it there and the next reader waits for ever.
- **Only one class of number is reported by a session.** The keys on a ticket are stored as they are, not one of them checked; the one exception is the reading some plugin wants as a metric — and only when its declaration ties that reading to a knob, and that knob has a value on the chain (some layer wrote it, or the declaration gives it a factory default; see "Plugins"). A number the plugin computes itself never travels by ticket, so it is never asked of a session either. The one who reports does not decide; the one who decides takes no readings.
- **Derived values are not written down.** "Ready" and "running" are labels computed at read time.

## 3. How a session is woken and closed out

**The prompt carries one invocation line and nothing else**: the node's title, the spec's path, the closing command, the user's instructions — the session reads all of them itself. There is a reason: anything padded into the prompt is a second copy of the same thing, and the older one.

**The user's instructions are read fresh, never injected.** Every session (the conductor and the subagents it dispatches) reads "what can I see from where I stand" itself, in the first batch of commands. **Position is two things: which line this session works, and which node is in its hand** — an instruction bound to a position can only be read out by a reader standing there. The closing step reads the same position: a constraint the session cannot see may not stop it at the close either (a closing instruction bound to another node does not take effect when this node is closed). When the position cannot be pinned down (two lines side by side, and no word about which node is in hand), **lean to the noisy side**: the cost of missing a real constraint is far higher than the cost of reading out one that has nothing to do with it. What is visible is pure derivation and is never written down — so there is no step where "the scope ended, someone has to write it off".

**What goes on that list, and what comes off it, only the user settles.** Archiving keeps an entry and stops reading it out; taking it off the list takes the body with it and leaves a trace of an id and a moment. That trace is for merging the records of two machines: when the other machine pulls, a deletion on this side is not cancelled by "it is still there" on the other, and the number is never handed out again to a new entry. The trace enters no human view, and a deletion is not a third status — an entry that is not on the list is not on the list. Putting one back (archived back to in force) is the user's to do as well; closing and opening both stay out of a session's hands.

**The close is two commands, and the order is nailed down: close the node → commit → push → dispatch.** The next session boots in the same worktree as the closing one and pulls first thing; a tree that is not committed clean either refuses to pull or reads half of it. So **dispatch is always the last thing**. What the closing step answers need not be a node to dispatch: when a threshold is crossed it only puts nodes into the graph, pins nothing, and the dispatch takes another command, with the picking settling it under the ordinary rules. Writing the ticket and closing the node are two commands so that the state in between (the ticket on disk, the node not closed yet) is stable in itself — when the chain breaks halfway, it is visible.

**A ticket is only a ticket: the step that hands it in drives nothing.** The session writes the ticket, reads the next step once (that answer is "waiting for a close" plus the one closing command), and hands back; what pushes the line to its next stable action — close the node, pick the next node, land that node's prompt — is the closing step, and the only writer of a prompt on disk is that closing chain. The step that writes the ticket writes not one byte.

**An old session is never revived**; every time a fresh one is opened: one conversation's context does not reach another node.

**Commands are always run by the tool; the session reads `action` only.** The answer an action returns carries no commands, and a write entry reports success only when it really moved the pointer / the ticket / the path / the line's state, and throws otherwise — the caller is never left holding a list it could run again. Every question the tool asks carries a bound: the few `doctor` puts to git turn one cell red, naming how long it waited, instead of hanging all night.

## 4. The two ways in

`--after` is a session closing its own node; every other `next` is the way in for driving the next step. The two ways treat "the line is in service" differently:

- **The closing way in does not look at the line's status.** The node itself says which line it belongs to; a line that has stopped and cannot even close the node it holds would leave that node pinned for ever. When the line is not in service this way **only records**: it records the step and marks the node, picks no next node and dispatches nothing, and writes not one character of the line's status — putting it back in service is a person's call.
- **The worktree mode is a knob, and the close still reads the record on disk alone.** `worktree_mode` takes `off` / `fork`, and the factory value is worked out per project: `fork` in a git project, `off` in anything else; this project and this machine can override it on either layer (see "Settings"). `reuse` is refused the moment it is read (`worktree_mode_unsupported`) — this engine works in those two modes only. Making the worktree, merging it back and cleaning it away are git the session types itself, and the tool owns only the record and the naming: the close looks at no worktree.
- **Every other `next` never drives a line that is not in service**; it answers `ask_user` with the command that puts the line back.

**The tool never writes "in service".** A line is in service the moment it is made, and after that only a person can put it back. The reason it stopped is not written into the state — it lives in the words spoken at the moment it stopped. A graph with no live work right now does not mean the line is dead: the graph grows, and whether to carry on is a person's decision.

pf-route runs the "put it back in service" command for the user, and the rule is the same: the decision comes from the user, pf-route is only the hand holding the pen, and the tool still decides nothing on its own. When the decision is made is settled too: pf-route talks about lines whenever it talks about nodes (which line this batch belongs to, whether a stopped line goes back, whether a new one opens), and the close only carries it out — whoever starts `/pf-conduct` reads a line already decided, and has no guessing to do.

## 5. Conclusions and stopping

- **Whether the work was done is decided by the record on disk**: the session writes on the ticket whether it delivered, and the tool marks the node by it without asking a second session. The conclusion is coarse; the fine judgement stays in the session's own report.
- **Whether the line carries on after a non-delivery follows the line's own policy**: stop and wait for a human, or carry on as if a node had delivered. Under either value the node is out of play waiting — the policy is about whether this line waits.
- **Whether the line runs on depends on this node's own `mode` alone**: `auto` has no human confirmation point, `manual`'s point sits in the session's conversation, and `checkpoint`'s point is the close itself — the whole round finishes and then waits once for a human to say "continue". An instruction and `--stop` can only **tighten** this rule, never loosen it.
- **The human's "continue" is written down.** The `checkpoint` gate sits on the line's own status, so the moment a person puts the line back in service is exactly the "continue" the tool is waiting for: the tool writes **this delivery** of that cell down as "approved by a human", and the rule is that the approval's moment is **not earlier than** this delivery's — both live on the node's own record. This is **counted by delivery, not by node**: deliver the same cell again and the delivery's moment moves past the approval, so the old approval lapses by itself, with nobody writing it off and no second record to keep in step. So "a human has let it through and the graph happens to have no work right now" and "this line cannot move by itself" are two readable facts — where before it could only be guessed from "did the line move one step further". Approving one cell (without going through the line) has its own verb: `dag approve`.
- **Stopping is one sentence**: the line is turned out of service. There is no paused / completed split — that fork asks "is there work left on the graph", and the graph grows and the work grows with it.
- **Picking the next node has one ranking and one place**: the tool takes the full ranking from the graph side, drops rows by readiness and by this line's pick set itself, and rewrites no scoring. Two implementations of one judgement are two places that drift apart.

## 6. The invariants

Each of these cost a bug; the reasoning already stated above is not repeated here:

1. A terminal ticket is the whole of "this node is done"; a mark left by a retry is always read as red, and replacing it starts with rolling the ticket back.
2. Done but not yet closed is a **stable state**: ask as often as you like and it answers the same wait plus the same command, writing not one byte.
3. Closing one node is not finishing the line: the line's other nodes do not move, and the relay sits on their own closes.
4. An instruction can **tighten** the stopping rule only, never loosen it; the node's own `mode` is the one place that judgement comes from.
5. Each tool reads its own record (the graph side cannot read the cycle record): only putting the two together shows who is working the node, and that putting-together lives in a reader who can read both records.

## 7. Recovery

**Redoing a node walks the same road**: roll the ticket back first (`cycle retry <cycle> <node>`; add `--drop` when the session is dead and the `started` mark is still there, and the claim goes with it), put the node back in play, pin it again, and push again. Verdicts are appended step by step — the tool reads no history, only "the line is holding it right now".

**A broken chain is a refusal.** A session that files no ticket is refused at the close on the spot (`nothing_to_settle`); a dispatch that cannot open anything hands its reason back as it stands, the panel's button says it to a reader, and the automatic relay leaves one log line. `started` is the only "already opened" evidence: while it is not on disk the plan still counts the cell as dispatchable and the next trigger walks it again; when it is on disk and the session really died, first take that claim away with `cycle retry <cycle> <node> --drop`, then pin and dispatch again the ordinary way — never force a second dispatch.

**There is no resident watchdog process — that is on purpose.** A watchdog would mean a second server watching every node, so a hung node does not surface by itself: with no ticket written there is no automatic detection at all, and the chain sits quietly at that node waiting for a human, whom a hand-run `/pf-conduct` can fish it back out.

## 8. Settings: one resolution chain

**A setting is a knob**, and a knob has one of four kinds: number, integer, word, switch. Knobs come from two places — the few the core reads itself, and the ones installed plugins claim in their declarations; the two merge into one table, and one name has one owner. That table is the scope of the resolution chain: **setting knobs and plugin knobs ride on the chain; this line's own three policies do not** (see the last item of this section).

- **Five landing points, narrower covering wider.** One node → this line → this project → this machine → factory default. The same name may be written on several layers at once, and which layer is in force is deterministic, not guessed.
- **Not every knob lands on every point.** Which layer takes a knob is written in that knob's own `layers`: the core's own settings (`max_agents` / `test_tier` / `worktree_mode`) are this project's and this machine's behaviour, and take the project and global layers only; a knob a plugin declaration brings is read by the plugin host through the whole chain, and by default all four layers land, with that cell in the declaration able to narrow it (say, this project's layer alone). Hand-written into a file that does not take that layer, the knob's name is named on the spot when that layer is read and skipped — a value nobody reads may not lie quietly on disk.
- **Every read answers a pair: the value in force, and which layer it came from.** Because "I set it, why is it not in force" is the one question this chain exists to answer; `config list` prints exactly that pair, and `config get` prints the value alone (that is the line a skill reads).
- **The write side has two commands.** `set` writes one value into exactly one layer, and `unset` takes that layer's entry away so the wider layer shows through again. Writing into a place that does not take the layer is refused by `set`, naming the layers the knob takes. A switch's `off` is a **value** (writing it turns the thing off), and taking the entry away is `unset` — two things, two spellings. With no layer flag the project layer is written; the line's layer rides on the line's record, taken by that record's one writer.
- **A value that cannot be read is said on the spot.** A value on a file layer that does not resolve makes the command fail and exit, computing nothing further: quietly falling back to the factory value would make the knob look "never configured". The one exception is the line's layer — it is a state record, records are read leniently, and a value that does not resolve counts as unwritten.
- **Some knobs have no factory value, some do.** Both spellings are legal for a plugin's threshold: with no `default` in the declaration, a knob nobody wrote sits quietly in "not configured" (read out as a dash), and only gains a value to judge once some layer writes a number; with a `default` it is in force from the moment the plugin is installed, which is why the ticket form keeps asking for it — the form asks for the number the judgement uses, and both sides read the same place.
- **This line's own three policies are not on the chain.** `parallel` (how many nodes it holds, how many sessions it opens at once), `when_shelved` (whether the line stops or carries on when a node comes back not delivered) and `spawner` (the spawner word this line names, `dsh` / `zcode` only) are written on the line's own record, and their readers read that record alone. Their door is `cycle policy`: `config` does not know these three names, and writing them on the project or global layer is read by nobody.

## 9. Plugins and the maintenance channel

**A plugin is a folder.** `plugins/<name>/` holds two things: the **declaration** (`plugin.json`, data: which timing it takes, which names it claims, which action it produces, the dedupe tag it writes outward, and the method each metric names), the **implementation** (`impl.mjs`, code: called once at the timing it takes), and the plugin's own files (the tools its `files` cell names). The folder's name is the plugin's identity — delete it and the plugin is gone, with no second place remembering it; put it back and it returns, with not one byte of the core changed. The skill a method names is the third piece, living in the same folder under `skills/<lang>/<method>/`. **The side that places it into the skill directory is this host** (`installPluginSkills` in `src/host/skills.ts`): each method folder is copied whole into `<dshHome>/skills/<method>/`, one language per installation, by the language this host runs in; the manifest is written at `<dshHome>/pathfinder/skills.json`, and unloading takes back exactly what the manifest lists — it is installed and removed together with the plugin.

**The core accepts kinds, never names.** The closed set has three parts: the four knob kinds above, two timings (close / dispatch) and two actions (insert / block). The two axes make exactly two cells: **insertion at the close, blocking at dispatch** — a declaration naming another cell is skipped at run time and named by the check-up. Knob names, readings, reading sources, dedupe tags and method names all merge in from declarations; which of those names the registry checks (the source of truth is `packages/pf-core/src/plugins/registry.ts`), no two plugins may share any of them, **and the same goes for a skill name**: one skill name has one owner, and two plugins carrying the same name are borrowing it — which is exactly what makes `<dshHome>/skills/<name>` unable to say whom it belongs to. A declaration is data, and the code that runs is in the implementation — "list what is installed" must not cost "run every one of them": a broken declaration may not take the help, the listing and the check-up down with it.

**A reading has one source, and the source may be the plugin's own.** A reading is either the number a session reports — only the session that ran the thing can measure it — or a number a tool computes. The core knows one source name of its own; a plugin that wants to measure something the core does not know claims a source name in its declaration and names the function in its implementation that computes it (the source of truth is the registry). **The core does not interpret that number**: the implementation is asked for it through the plugin host's one reading door, whatever comes back is handed back as it is, and a value of the wrong type reads as "not known this run", the same rule as the number a session reports. A source name is owned by the plugin that claims it — so two numbers can never be confused about whose they are; delete that folder and the source goes with it. A reading's source can only be the core's own plus the ones the plugin itself claims: a name another plugin claimed is not borrowable, and is judged exactly like a name nobody knows — the check-up names it, this plugin is not asked this round, and the line runs to its end as usual.

**A declaration can also claim command words.** Besides the above, a declaration may report a few command words: `<word> …` hands the line to that folder's implementation (the same `impl.mjs`, this time running its `main`). **A declaration that claims words need not take a timing** — it is never asked inside the pipeline, so timing and action may both be left out; a declaration claiming no word still has to take that cell, and the missing half is named. Who answers on this face, which line the help prints, who wins a clash, and who reports it, are on the sheet `doctor` prints.

**Insertion closes the step.** An insertion at the close timing is answered back by the closing command itself: in one call each answering plugin contributes one node (the action is `insert_node`, nothing was pinned), and as many debts as are over the line are inserted at once. The inserted node hangs behind the node just closed, with no "next node originally picked" edge to split — the next pick settles who runs next by the ordinary ranking. **A plugin that wants the line to keep dispatching has to stop answering while its own node is still on the graph** — that is what the metrics that recognise their node by dedupe tag do (see "one metric keeps one debt node at a time" below), and the core will not guess this on a plugin's behalf.

**Tolerant at run time, strict in the check-up.** A plugin whose declaration cannot be read is skipped this round, saying nothing; an implementation that will not load, or that throws when it answers (ending itself with `process.exit` counts), still lets the close and the dispatch run to their end: one `WARNING:` line hangs on that close's / dispatch's return value (it is data, for the caller to print), that plugin contributes nothing this round, and no other plugin and no line is affected — a project in the middle of its pipeline may not be held up by one broken plugin. Where it is broken is decidable, so that belongs to `doctor`: which plugins are installed, how each one works (the summary and knobs of its declaration), its dedupe tags and method names, the reading sources it claims, and every problem it knows about, are all on that sheet. **The validator checks these, and every problem about a plugin names which plugin**: whether a declaration steps outside the core's closed sets (the timing it takes, the names it claims, the action it uses), whether two declarations fight over one name (reading sources included), whether the implementation file named by the declaration is there and loads, whether every claimed source has the function it names in the implementation (only whether it is there, with no real call — the number comes from the round that runs it); whether every method a declaration names has that skill in its own plugin's `skills/<lang>/` (a name landing on another plugin's skill is borrowing, and skills do not travel across plugins), and whether one skill name is carried by two plugins at once; **a skill nobody names is not a problem** — the plugin folder is its listing, and that is the one the plugin ships for the user to call directly; and then a stand-in project with one real call to the implementation — it has to answer or have nothing to say this round, it may not throw, and its answer may not edit the graph, since that edit has one implementation, the core's. **The validation lives outside the pipeline**: the validator is one set shared by the test suite and by `doctor`, and no step of the route runs it — somebody else's project may be mid-pipeline, and a badly written plugin should not stop it; this has nothing to do with how fast it runs.

**On/off is a switch knob**, riding the chain of the section above: node → this line → this project → this machine → factory default, covered at any layer; a plugin with no switch is always on. A plugin need not know it can be turned off: the chain turns it off, and the implementation still only answers when its timing comes.

**The blocking timing sits at dispatch: whether a session may open now is the plugin's to say.** A plugin may answer "no" at the dispatch timing, and its reasons land one by one in the `dispatch_blocked` refusal; the line stays in service — a time-window gate ("not now, ask again later") has to answer exactly this way. **The gate is a cheap, idempotent, read-only check, asked before the material lands and before a session opens**: `conductor.dispatch` asks it once, after reading the claim; a blocked dispatch therefore writes no prompt and opens no session, the node just pinned stays pinned (pinning was the previous step), and the next dispatch asks again. It may not count, may not write to disk, and may not change its answer because it was already asked — the same state asked several times must answer the same.

### The maintenance channel

**A debt on the maintenance channel is one metric in a plugin's declaration.** A plugin that takes the close timing reads at the close whether its own debt is over the line; if it is, it wants a debt node. **Every debt measures and judges itself**: where the number comes from (the number a session reports, or one its own tool computes), how it is judged, how the wording goes, and what counts as paid off, all belong to the plugin that claims it, and nobody has to know another debt.

- **Debt is project-level.** Maintenance is the project's debt: it belongs to no line and has no edges, so the graph's picking always pushes it to the bottom. This channel gives it one way in: **at the close, following the line this cycle configured for it, it is inserted as a node**.
- **Each judges its own.** The switch, the line, the dedupe tag and the method name each belong to its own plugin (the names live in their own declarations, and `doctor` prints them). In one close each plugin looks at its own debt, and each inserts one node — over the line on several, and that close inserts several.
- **The judgement sits where it can be computed.** The close reads what it happens to hold at that moment (this node's ticket, the graph snapshot), a session hands over only the number it can measure, and never decides whether maintenance is due.
- **With not one knob configured the close changes by not one byte.** A debt with no line configured is not in force, and the close's answer is byte for byte what it is without it — that is each debt's own regression floor. The same for the one whose switch is off: over the line it inserts nothing and does not ask for that reading either — the debt is still there, this project just does not want it in this time.
- **The inserted node hangs behind the node just closed.** There is one edge (the closed node → the new node), with no "next node originally picked" edge to split; the score is computed by the graph's algorithm from the edges. **The ranking changes nowhere**: where it ranks and whether it is next are settled by the same ranking at the next pick.
- **Two nodes inserted by one close are siblings.** Both hang behind the node just closed, and neither waits for the other.
- **An inserted node carries this line's own tag.** Picking is a separate step: a node carrying the metric tag alone is invisible to this line's filter set and is never picked; with the line's tag it falls inside this line's pick set.
- **One metric keeps one debt node at a time**: the node's dedupe tag answers this — with one on the graph carrying it, this crossing waits.
- **The generated spec walks the ordinary node road.** One sentence of scope (this run only pulls this one debt back inside the line), a completion rule that can be followed, and a paragraph on "why this node exists" — which measurement, what it read, where the line is; the spec also carries the line naming the skill, and the session running this node follows it. The template does not guess this node's own preparation (no function names, no file paths, no line numbers); work that cannot be written into a criterion never comes through this channel.
